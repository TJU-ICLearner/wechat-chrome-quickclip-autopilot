# 微信公众号 → Obsidian 自动归档：运行说明

本说明对应 `wechat-chrome-quickclip-autopilot` skill。它把手机微信里筛选出的
公众号文章，自动归档为 Obsidian 的原始资料和 LLM Wiki 页面。vault 路径由
`OBSIDIAN_VAULT_DIR` 配置；未设置时默认为 `~/Documents/SOC Learning`。

## 1. 目标与边界

主入口是用户直接在本 Codex 对话粘贴公众号链接：

```text
https://mp.weixin.qq.com/s/...
```

cc-connect/微信可保留为可选入口，但不再是日常使用所必需的组件。

系统负责其余步骤：在用户的日常 Chrome 中打开文章、调用已安装的
Obsidian Web Clipper、确认原文落盘、生成摘要和知识图谱链接，并回复
一条最终结果。在 Codex 对话中回复不受微信 iLink 的低发送额度影响。

这不是后台无界面浏览器方案。Chrome 会被切到前台，文章会在用户的
正常 Profile 中打开；这样才能使用用户现有的登录状态和 Web Clipper
扩展。用户无需再点击剪藏或打开 Obsidian。

## 2. 架构

```text
Codex 对话（主入口）                 微信/cc-connect（可选入口）
  │  粘贴 mp.weixin.qq.com 链接          │  /new + 链接
  └──────────────────────┬──────────────┘
                         ▼
                  Codex + 本 skill
  │
  │  调用本地 Quick clip 脚本
  ▼
日常 Chrome Profile（前台）
  │  打开文章 → 等待 3 秒 → 发送 ⌥⇧O → 恢复此前前台应用
  ▼
Obsidian Web Clipper
  │  直接写入 raw/articles/
  ▼
Codex 同一任务
  │  验证原文 → 生成摘要、标签、概念与链接
  ▼
wiki/ + 原始入口中的完成消息
```

## 3. 关键文件与职责

| 位置 | 职责 |
| --- | --- |
| `~/.cc-connect/config.toml` | 可选的 cc-connect WeChat 项目配置。令牌不得写入说明、日志或聊天。 |
| `<vault>/AGENTS.md` | Vault 内的强制路由规则：收到公众号链接时先调用本地剪藏脚本，剪藏后在同一任务整理。 |
| `wechat-chrome-quickclip-autopilot/scripts/clip-wechat-in-chrome.zsh` | Skill 自带的执行脚本：打开当前日常 Chrome、发送 Quick clip 快捷键、轮询确认原文。 |
| `<vault>/raw/articles/` | 不可改写正文的原始文章，必须带原始 URL。 |
| `<vault>/wiki/` | AI 维护的摘要、概念、实体、索引、总览与日志。 |
| `wechat-obsidian-autopilot` skill | 对已确认 raw 文章进行 wiki 层整理。 |

历史上创建过 `com.mxt.obsidian-wechat-organizer` 目录监控启动项；它已
停用。macOS 的后台进程无法稳定访问 `Documents`，因此它不能作为完成
信号来源，也不能代替同一 Codex 任务的整理步骤。

## 4. 一次性前置设置

### 4.1 Chrome 与 Web Clipper

1. 使用平时保存了公众号登录状态、已安装 Obsidian Web Clipper 的 Chrome
   Profile。不要使用任何专用自动化 Profile。
2. 在 Web Clipper 中设置默认 vault 为 `SOC Learning`，目标文件夹为
   `raw/articles`。
3. 确认 Quick clip 快捷键为 `⌥⇧O`。在任意可保存网页上手动按一次，确认
   它无需打开面板或确认弹窗即可直接写入指定文件夹。
4. 不要让另一个程序持续抢占 Chrome 前台；触发后的约 3 秒内，文章页
   应保持为活动标签页。

### 4.2 macOS 辅助功能授权

脚本通过 `/usr/bin/osascript` 向 Chrome 发送 `⌥⇧O`。因此只需一次性在：

```text
系统设置 → 隐私与安全性 → 辅助功能
```

允许 `osascript` 控制电脑。若系统显示“osascript 不允许发送按键”，这是
未授权状态，不是公众号页面错误。

脚本不会读取浏览器 Cookie、密码、Profile 文件或登录凭据。

### 4.3 本地命令依赖

当前脚本需要 macOS 自带的 `zsh` 与 `osascript`，以及已安装的 `rg` 与
`jq`。它们用于验证参数、确认保存的 Markdown 和输出结构化状态；不用于
从网络抓取文章。

## 5. 每篇文章的执行细节

### 5.1 接收与校验

skill 接受用户直接发到本 Codex 对话的单一、`https://mp.weixin.qq.com/`
开头链接；cc-connect 的 `soc-learning` 项目是可选的同等入口。其他内容不应
误触发剪藏。

### 5.2 本地剪藏命令

实际命令为：

```zsh
"${CODEX_HOME:-$HOME/.codex}/skills/wechat-chrome-quickclip-autopilot/scripts/clip-wechat-in-chrome.zsh" \
  'https://mp.weixin.qq.com/s/…'
```

脚本的固定行为：

1. 检查 URL 域名；不符合则返回 `error`。
2. 用锁目录防止两篇文章同时争抢前台 Chrome；若已有任务，返回 `busy`。
3. 在当前最前面的日常 Chrome Profile 打开链接并激活 Chrome。
4. 默认等待 3 秒，让公众号文章的动态正文渲染；发送快捷键后恢复此前的前台应用。
5. 通过 `System Events` 发送 `⌥⇧O`。
6. 最多等待 60 秒，按**原始 URL**而非猜测标题，在 `raw/articles` 内寻找
   新写入的 Markdown。
7. 找到后返回 `captured` 及绝对文件路径；找不到则返回 `pending`。

脚本会在 `<vault>/.claudian/logs/wechat-chrome-clipper.log` 记录请求、
确认成功或未确认的时间。日志位于 vault 内，是因为 cc-connect 的 Codex
任务使用 `workspace-write` 沙箱；它不能也不应写入 `~/.cc-connect`。日志
不会记录 WeChat 令牌或浏览器私密信息。只有经 cc-connect 进入的任务才会受到
该服务的 `workspace-write` 沙箱约束。

### 5.3 状态码与处理规则

| 状态 | 含义 | 正确动作 |
| --- | --- | --- |
| `captured` | 找到包含该原始 URL 的新 raw Markdown。 | 只读取该文件，执行 wiki 整理。 |
| `busy` | 另一条剪藏尚未结束。 | 不重复发送快捷键；告知用户稍后重试。 |
| `permission_required` | macOS 拒绝发送按键。 | 用户授予一次 osascript 辅助功能权限后重试。 |
| `chrome_unavailable` | AppleScript 无法操作 Google Chrome。 | 打开带 Web Clipper 的日常 Chrome Profile，并使其成为最前窗口后重试。 |
| `pending` | 快捷键已发送，但 60 秒内没有确认的 raw 文件。 | 检查 Quick clip 文件夹、模板和 Chrome Profile；不要改用 HTTP 抓取。 |
| `error` | URL 不符合预期或本地输入错误。 | 直接说明错误。 |

`captured` 仅表示原文已落盘，不表示 wiki 已完成。完成条件是原文、源摘要、
索引和日志都已验证。

### 5.4 整理

成功剪藏后，使用 `wechat-obsidian-autopilot` 只处理返回的那一个 raw 文件：

- 保留原文正文，不改写事实、观点、数据或代码；仅允许 vault schema 中的
  格式修正。
- 新建/更新 `wiki/sources/<标题>.md`，并链接到对应 raw 文件。
- 写出一句话概括、核心观点、边界、可行动项和合理标签。
- 只在真正有助于未来检索时更新概念/实体页。
- 每次都更新 `wiki/index.md`、`wiki/log.md`，必要时更新 `wiki/overview.md`。
- 检查所有新增 wikilink 的目标存在。

完成后在原始入口报告文章标题、最重要的一句话、已创建或更新的主要页面，以及
任何实际限制。直接在 Codex 对话的任务可正常报告；经微信进入的任务仅发送一条
最终消息，以节省 iLink 发送额度。

## 6. 如何确认“已处理完成”

以文件结果为准，而不是以“已发送剪藏命令”为准：

1. `raw/articles/` 有含原始 `mp.weixin.qq.com` 链接和实质正文的文件。
2. `wiki/sources/` 有对应标题的摘要文件，并链接回 raw。
3. `wiki/index.md` 有该源的条目。
4. `wiki/log.md` 有对应日期的 `ingest` 记录。

命令行检查示例：

```zsh
rg -l -F 'https://mp.weixin.qq.com/s/…' \
  --glob '*.md' '<vault>/raw/articles'
rg -n -F '文章标题' \
  '<vault>/wiki/index.md' \
  '<vault>/wiki/log.md'
```

## 8. 故障排查

### 8.1 打开的是没有插件的 Chrome

原因通常是之前启动过带 `--user-data-dir` 的专用 Profile，或者当前最前面的
窗口不是日常 Profile。关闭测试/专用窗口，打开平时带 Web Clipper 的窗口，
并使其成为最前窗口后再试。脚本不应启动新的 Chrome Profile。

### 8.2 Chrome 打开文章，但没有保存文件

依次检查：

1. 手动按 `⌥⇧O` 是否会直接保存。
2. Web Clipper 默认 vault 是否为 SOC Learning。
3. Web Clipper 默认文件夹是否精确为 `raw/articles`。
4. 页面是否仍在加载，必要时通过 `WECHAT_CLIP_WAIT_SECONDS` 适当增加默认的 3 秒等待时间。
5. Web Clipper 是否弹出模板/保存确认面板；若会，需先把 Quick clip 配置为
   无确认直接保存。

不要把故障降级为 HTTP 抓取：公众号通常会跳转验证码页面，且会丢失用户正常
登录 Profile 的能力。

### 8.3 `permission_required`

在 macOS 辅助功能中允许 `/usr/bin/osascript` 后重试。不要尝试模拟、绕过或
关闭系统安全提示。

### 8.4 微信 CAPTCHA、登录页或正文不完整

用户必须在日常 Chrome 亲自完成登录或验证码。自动化仅能在成功渲染的文章页
上调用 Web Clipper，不能规避验证。

### 8.5 `busy`

等待当前任务结束后再发下一篇；不要并发发送多条链接。当前设计刻意串行化，
避免快捷键发送到错误文章。

### 8.6 raw 已生成但没有 wiki

这通常表示原始 Codex 任务被中断。直接对那个 raw 文件调用
`$wechat-obsidian-autopilot` 即可恢复。不要重新剪藏同一个链接。

## 9. 维护与修改

- 修改 Quick clip 等待时间：编辑 Skill 中的
  `scripts/clip-wechat-in-chrome.zsh` 的默认等待值，或设置
  `WECHAT_CLIP_WAIT_SECONDS`；一次只小幅调整并用真实链接验证。
- 修改目标文件夹：同时调整 Web Clipper 设置与脚本里的 `raw_dir`，并更新
  `AGENTS.md` 与本说明。两处不一致会得到 `pending`。
- 修改整理规则：先更新 vault 的 `CLAUDE.md`/`AGENTS.md`，再更新
  `wechat-obsidian-autopilot`，最后用一篇新文章验证。
- 修改 cc-connect（可选）：只编辑项目路由、显示或发送额度；不要在文档或日志
  中记录 token、账号 ID 或允许列表。
- 停用可选微信入口：停止 cc-connect daemon 或移除项目路由；直接在 Codex
  对话的入口不受影响。不要删除已归档的 raw 与 wiki 页面。

## 10. 安全与行为约束

- 用户的选择权在文章筛选阶段；系统不会自行发现、推荐或批量抓取公众号文章。
- 所有处理局限于用户提供的链接和 SOC Learning vault。
- 不传出 vault 内容、cookie、账号信息或剪藏正文到第三方服务。
- 不删除 raw 资料；来源冲突时保留已有文件并创建明确的不同文件名。
- 不绕过 CAPTCHA、登录、验证码、付费墙或浏览器安全提示。
- 公众号正文的成功标准是 Web Clipper 的真实 Markdown，而不是 URL 已打开。
